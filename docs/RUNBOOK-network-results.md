# Результаты сетевого прогона — 16 сентября 2026

Прогон выполнен владельцем на плате по [RUNBOOK-network.md](RUNBOOK-network.md).
Исходные материалы: [net-inspect.txt](net-inspect.txt) — инвентаризация до правки,
[monitoring-net-test.log](monitoring-net-test.log) — отчёты всех четырёх режимов.

## Итог

**SSH через Tailscale не зависит от mihomo.** Во всех четырёх режимах вход извне
проходил. Ключевой из них — `vpn-down`: VPN был закрыт по-настоящему,
и это подтверждено измерением, а не предположением.

| Режим | SSH извне | tailscale | Worker через VPN | mihomo |
| --- | --- | --- | --- | --- |
| baseline | соединился | Running | 200 | active |
| no-mihomo | соединился | Running | 200 | inactive |
| vpn-down | соединился | Running | недоступен | active |
| restart-mihomo | соединился | Running | 200 | active |

Адрес платы в tailnet: 100.95.251.48. Второй узел — kukusik, 100.95.133.40.

## Шаг 1: fake-ip снят

До правки все три имени отдавали поддельные адреса; после — настоящие:

```
before  controlplane.tailscale.com  fake-ip      после  real
before  login.tailscale.com         fake-ip      после  real
before  derp1.tailscale.com         fake-ip      после  real
```

Резервная копия конфигурации: `/root/mihomo-backup/config.yaml.20260916T035548Z`.
`mihomo -t` подтвердил корректность до перезапуска.

После этого `tailscale up` сразу выдал ссылку авторизации и завершился `DONE` —
то, чего не происходило накануне. Диагноз подтверждён исправлением.

Отдельно проверено 16 сентября, что новые адреса настоящие, а не вторая подмена:
имена отдают меняющиеся адреса из 192.200.0.0/24, и TLS-соединение с 192.200.0.114
проходит проверку сертификата с `CN=controlplane.tailscale.com`. Это round-robin
по фронтендам Tailscale.

## Что доказал каждый режим

**baseline.** Обычное состояние: весь трафик в TUN, трафик Tailscale мимо него.
Worker отвечает 200. Вход извне работает.

**no-mihomo.** Служба остановлена, TUN исчез, маршрут к 1.1.1.1 стал прямым
через wlan0. SSH продолжал работать. Попутный факт: Worker остался доступен
и без VPN (200) — Cloudflare из этой сети достижим напрямую.

**vpn-down.** Закрыто 14 адресов VPN-серверов blackhole-маршрутами.
Блокировка сработала по-настоящему: Worker стал недоступен, и так оставалось
все 180 секунд. Tailscale при этом Running, SSH извне соединялся.
Опасение, что blackhole не поймает сокет с `auto-detect-interface`,
не подтвердилось — проверка в скрипте показала реальный отказ, а не фикцию.
Агент оставался active: доставка встала, данные копились в очереди, как задумано.

**restart-mihomo.** Tailscale пережил перезапуск: Running и на 20-й, и на 180-й
секунде, адрес не менялся, Worker вернулся к 200.

Во всех режимах откат отработал: `restored; mihomo=active tailscaled=active`,
`internet via VPN: 200`, выход с кодом 0. Таймер страховки не понадобился.

## Прямое соединение, а не DERP

`tailscale ping` до второго узла: `pong from kukusik via 192.168.100.151:41641 in 5ms`.
Соединение прямое. Но оговорка существенная: второй узел находится в той же
локальной сети, поэтому проверен прямой путь по LAN, а не через интернет.
Прямой путь между разными сетями и работа через DERP при закрытом UDP
остаются непроверенными.

Таблица маршрутизации 52 появилась после входа: маршруты к пиру
и к 100.100.100.100 (MagicDNS).

## Что осталось непроверенным

1. Перезагрузка платы при недоступном VPN — пятый сценарий, скриптом не покрыт.
2. Прямое соединение между разными сетями и работа через DERP при закрытом UDP.
3. Смена подсети DHCP: `route-exclude-address` прибит к 192.168.100.0/24,
   при смене подсети пропадёт и SSH по локальной сети.
4. Проверка через реальный модем.
5. Срок действия ключа узла Tailscale для долгой автономной работы.

## Ошибки в скриптах, найденные по этим результатам

- `probe_health` печатал `000unreachable`: curl выводит `000` при отказе
  соединения и одновременно возвращает ненулевой код, из-за чего срабатывала
  ветка `|| echo`. На решение о зачёте прогона это не влияло —
  сравнение с `200` работало правильно, — но в отчёте выглядело мусором.
  Исправлено: теперь `unreachable`.
- `relayed_peers` в отчёте не значил ничего: поле `Relay` заполнено домашним
  DERP даже при прямом соединении. Счётчик убран, вместо него число узлов;
  прямое соединение определяется командой `tailscale ping`.
- В `net-inspect.sh` фильтр учётных данных вырезал любую строку со словом
  `server`, включая ключи `nameserver:` и `default-nameserver:`. В выводе
  их значения повисали без заголовков под `fake-ip-range`. Фильтр привязан
  к ключу в начале строки.

## Замечание по безопасности

sshd слушает порт 22 на всех адресах с `PermitRootLogin yes`
и `PasswordAuthentication yes`. Пока доступ был только из локальной сети,
это одно; теперь плата видна в tailnet. Стоит пересмотреть отдельно.
