# SSH через Tailscale и независимость от mihomo

Используется обычный OpenSSH внутри Tailscale. Публичный IP дома,
обратный SSH на VPS и Cloudflare Tunnel для этого не требуются.
Фактические этапы записываются в [STATUS.md](../STATUS.md).

## Установка и вход

На Debian 13 используется [официальный репозиторий](https://pkgs.tailscale.com/stable/)
Tailscale для trixie, пакет arm64 для текущей Orange Pi 4 Pro.

```sh
sudo systemctl enable --now tailscaled
sudo tailscale up --accept-dns=false --accept-routes=false
```

Авторизовать плату и компьютер администратора в одном tailnet.
Не включать exit node, subnet routing и Tailscale SSH: порт 22 обслуживает sshd.
Проверить tailscale status, tailscale netcheck, tailscale ip -4,
затем открыть новую сессию ssh dmw@<tailscale-ip>.
Fingerprint сверить через доверенное LAN-соединение.
Проверить срок действия ключа платы для долгой автономной работы.

## Обход TUN

Настройка ещё требует испытания; прежние monitoring-route, monitoring-tunnel,
prepare-mihomo.py и activate-mihomo.sh рассчитаны на VPS и не применяются здесь.

Tailscale использует policy rules, отдельную таблицу маршрутизации и метки
исходящего транспорта. До активации mihomo проверить ip -4 rule, ip -6 rule,
маршруты установленной версии и правила nftables. Tailscale должен обрабатывать
свой транспорт и tailnet до перехвата TUN. Исключение всего UID root
не заменяет эту проверку.

Отдельно проверить DNS для control plane и DERP при неработающем VPN:
--accept-dns=false само по себе не защищает DNS от mihomo fake-ip/dns-hijack.
Нужен проверенный прямой DNS управляющего канала или соответствующее исключение.
Адреса DERP меняются; одного IP-исключения недостаточно.

Платный VPN переносится из ~/mihomo с сохранением оригинала.
Orange Pi требует бинарник ARM64 и проверку через mihomo -t.
Первую активацию выполнять с таймером отката и сохранённой LAN-сессией,
после успешной проверки Tailscale без mihomo.

## Что уже измерено на плате

Проверено 14 сентября чтением состояния, без изменений. Правила Tailscale стоят
на приоритетах 5210–5270, правила mihomo — на 9000–9010, поэтому Tailscale
разбирает свой транспорт раньше, чем TUN успевает перехватить:

| Назначение | Обычный пакет | Пакет с меткой Tailscale 0x80000 |
| --- | --- | --- |
| 1.1.1.1, 8.8.8.8 | через Meta, таблица 2022 | напрямую через wlan0 |
| 192.168.100.0/24 | напрямую через wlan0 | напрямую через wlan0 |

iptables и nft на плате не установлены: mihomo работает только политиками
маршрутизации, скрытого перехвата в netfilter нет. Таблица 2022 покрывает
всё, кроме локальной сети, поэтому DNS к роутеру 192.168.100.1 идёт мимо TUN,
а к публичному резолверу — в TUN. systemd-resolved сейчас настроен на роутер,
значит имена control plane и DERP резолвятся независимо от VPN.

Это расчёт по таблицам маршрутизации, а не испытание. Пока Tailscale
не авторизован, таблица 52 не существует и проверить нечего.

## Fake-ip: скрытая зависимость

Конфигурация mihomo использует `enhanced-mode: fake-ip` с диапазоном
198.18.0.0/16 и `dns-hijack: any:53`. Доменов Tailscale в `fake-ip-filter` нет.

Если запрос имени control plane попадёт в TUN, Tailscale получит поддельный адрес,
и метка 0x80000 уже не поможет: обход отправит пакет в таблицу main, где для
198.18.0.0/16 маршрута нет вовсе — есть только 198.18.0.0/30 на Meta. Связь
пропадёт, а выглядеть это будет как отказ Tailscale, а не как подмена DNS.

Сейчас этого не происходит только потому, что `route-exclude-address: 192.168.100.0/24`
выводит локальную сеть из таблицы TUN, а systemd-resolved ходит к роутеру
192.168.100.1. Защита держится на одном условии: DNS остаётся локальным.

**Это перестало быть предположением 15 сентября.** После перезапуска mihomo
зарегистрировал свой DNS в systemd-resolved как Link 6 (Meta) с сервером
198.18.0.2, и имена Tailscale стали получать поддельные адреса:

```
controlplane.tailscale.com  ->  198.18.0.91
ip route get 198.18.0.91                 -> via 198.18.0.2 dev Meta
ip route get 198.18.0.91 mark 0x80000    -> via 192.168.100.1 dev wlan0
```

`tailscale netcheck` продолжал работать и показывал честные задержки DERP,
потому что CLI не метит свои пакеты и идёт через TUN, где mihomo разворачивает
fake-ip обратно в домен. `tailscaled` метит сокеты, обход уводит его на роутер,
и там пакет к 198.18.0.91 исчезает без ответа. Вход висит без единой ошибки —
самый неудобный вид отказа: плата выглядит здоровой.

Отсюда задачи:

1. Внести `+.tailscale.com` и `+.tailscale.io` в `fake-ip-filter`.
   Это делает `deploy/mihomo-tailscale-dns.py`: резервная копия, `mihomo -t`
   до перезапуска, возврат копии при отказе. Фильтр по доменам, а не по адресам,
   переживает смену адресов DERP.
2. `route-exclude-address` прибит к 192.168.100.0/24. При смене подсети DHCP
   пропадёт и SSH по локальной сети; это отдельный сценарий приёмки.
3. Проверять имена control plane после каждого изменения mihomo: DNS-линк
   появляется заново при перезапуске службы.

Менять конфигурацию следует после измерения текущего состояния, иначе непонятно,
что именно проверяется. Оригинал конфигурации хранить вне Git: он содержит
боевые адреса серверов, UUID и пароли. В .gitignore добавлены config.yaml,
mihomo/ и cache.db.

## Испытание

Пошаговый порядок с местом для записи результатов —
[RUNBOOK-network.md](RUNBOOK-network.md). Ниже — устройство проверки.

Скрипты: `deploy/net-inspect.sh` только читает состояние, `deploy/net-failover-test.sh`
проводит опасные состояния. Второй **до** любого изменения ставит независимый
таймер systemd, который возвращает плату, даже если сессия, запустившая тест,
погибнет. Обработчик выхода восстанавливает состояние и снимает таймер.

Запускать отсоединённо, иначе обрыв связи прервёт сам тест:

```sh
sudo bash deploy/net-inspect.sh > /tmp/net-inspect.txt

sudo tailscale up --accept-dns=false --accept-routes=false --timeout=30s
tailscale status; tailscale ip -4

sudo systemd-run --unit=monitoring-net-test --collect \
  /home/dmw/projects/monitoring/deploy/net-failover-test.sh baseline --hold 180
journalctl --no-pager -u monitoring-net-test -f
```

Затем те же режимы: `no-mihomo`, `vpn-down`, `restart-mihomo`. Отчёт каждого
прогона дописывается в /var/log/monitoring-net-test.log.

Входящий SSH нельзя проверить с самой платы. Пока идёт окно удержания,
с компьютера администратора выполнить `ssh dmw@<tailscale-ip>` и записать
результат. Порядок состояний: baseline, no-mihomo, vpn-down, restart-mihomo,
затем перезагрузка платы при недоступном VPN. Проверить прямой Tailscale UDP,
DERP, DNS, смену DHCP и реальный модем.

Режим vpn-down находит адреса VPN в конфигурации, а если их там нет —
по действующим соединениям mihomo, и закрывает их blackhole-маршрутами.
Адреса в отчёт не попадают.

У этой блокировки есть известное слабое место: при `auto-detect-interface: true`
mihomo привязывает исходящий сокет к wlan0, а blackhole-маршрут не имеет
устройства и может такой сокет не поймать. Поэтому сразу после блокировки
скрипт обращается к Worker: этот трафик выходит только через VPN. Ответ 200
означает, что VPN жив и прогон ничего не доказывает — отчёт пишет об этом прямо.
Запасной путь в таком случае — установить nftables и закрыть адреса в output.

Сбой VPN задерживает доставку: для этого есть суточная очередь.
Блокировка самого Tailscale и потеря интернета остаются отдельными отказами.

## Изменения 17 сентября

В ночь на 17 сентября другая сессия дважды заменила конфигурацию mihomo
(копия прежней — `/etc/mihomo/config.yaml.bak-20260917-020405`), замаскировала
`fake-hwclock-load` и перевела NTP на IP-адреса. Причина — откат системного
времени при загрузке: fake-hwclock ставил время прошлого выключения поверх
верных аппаратных часов, из-за чего часы прыгали на часы вперёд после первой
синхронизации. После замены исправление fake-ip на месте: имена Tailscale
отдают настоящие адреса. Подробности — STATUS.md, разбор потерь 16–17 сентября.

## Результат испытаний

Прогон выполнен 16 сентября, подробности и исходные материалы —
[RUNBOOK-network-results.md](RUNBOOK-network-results.md).

Независимость SSH от mihomo подтверждена в четырёх состояниях: обычном,
без mihomo, при закрытом VPN и после перезапуска mihomo. В каждом вход извне
проходил. Режим с закрытым VPN засчитан по измерению: Worker был недоступен
все 180 секунд, то есть VPN действительно не работал.

Прямое соединение с пиром проверено `tailscale ping` — 5 мс без DERP, но пир
находился в той же локальной сети. Прямой путь между разными сетями и работа
через DERP при закрытом UDP не проверены и в достигнутое не засчитываются,
как и перезагрузка платы при недоступном VPN, смена подсети DHCP и реальный модем.
