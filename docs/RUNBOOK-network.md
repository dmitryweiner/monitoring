## Шаг 0. Инвентаризация, ничего не меняет

```sh
cd /home/dmw/projects/monitoring
sudo bash deploy/net-inspect.sh > /tmp/net-inspect.txt 2>&1
tail -40 /tmp/net-inspect.txt
```

Сохранить `/tmp/net-inspect.txt` — содержимое `/etc/mihomo/config.yaml`
в нём печатается без учётных данных. Файл лежит в `/tmp` и исчезнет
при перезагрузке: скопировать в домашний каталог, если нужен.

## Шаг 1. Снять блокировку входа

Выполнено 15 сентября: без этого шага вход в Tailscale висит без ошибок.
mihomo отдаёт на имена Tailscale поддельные адреса из 198.18.0.0/16, а метка
tailscaled уводит пакет мимо TUN на роутер, где такой адрес некуда девать.

```sh
sudo python3 deploy/mihomo-tailscale-dns.py --dry-run
sudo python3 deploy/mihomo-tailscale-dns.py
```

Скрипт сам проверяет результат. Признак успеха — имена отвечают настоящими
адресами, а не из 198.18.0.0/16:

```sh
getent ahostsv4 controlplane.tailscale.com
```

Проверять это заново после каждого перезапуска mihomo.

## Шаг 2. Вход в Tailscale

Потребуется открыть ссылку авторизации в браузере.

```sh
sudo tailscale up --accept-dns=false --accept-routes=false --timeout=30s
tailscale status
tailscale ip -4
tailscale netcheck
```

Не включать exit node, subnet routing и Tailscale SSH: порт 22 обслуживает sshd.
Авторизовать плату и компьютер администратора в одном tailnet.
Fingerprint сверить по доверенному соединению в локальной сети.
Записать выданный адрес Tailscale — он нужен на каждом следующем шаге.

После входа появится таблица маршрутизации 52; до входа её нет.

## Шаг 3. Четыре режима, по одному

Каждый режим **до** любого изменения ставит независимый таймер systemd,
который возвращает плату через «удержание + 2 минуты», даже если сессия,
шелл и сам скрипт погибнут. Обработчик выхода ловит SIGTERM и SIGINT.

Запускать отсоединённо, иначе обрыв связи прервёт сам тест:

```sh
sudo systemd-run --unit=monitoring-net-test --collect \
  /home/dmw/projects/monitoring/deploy/net-failover-test.sh baseline --hold 180
journalctl --no-pager -u monitoring-net-test -f
```

Порядок: `baseline` → `no-mihomo` → `vpn-down` → `restart-mihomo`.
Между запусками дождаться завершения предыдущего:

```sh
systemctl --no-pager status monitoring-net-test | head -5
```

Отчёты всех прогонов копятся в `/var/log/monitoring-net-test.log`.

### Что делать во время окна удержания

**Главный результат каждого режима снимается не с платы.** Пока идёт удержание,
с компьютера администратора выполнить и записать результат:

```sh
ssh dmw@<tailscale-ip>          # получилось или нет, за сколько секунд
ping -c 3 <tailscale-ip>
```

С самой платы входящий SSH проверить невозможно.

### Отдельно, вручную

Четыре режима выше пройдены 16 сентября. Осталось, и скриптом не покрыто:

- перезагрузка платы при недоступном VPN;
- прямое соединение между разными сетями и DERP при закрытом UDP:
  проверенный 16 сентября прямой путь был внутри локальной сети;
- смена подсети DHCP — `route-exclude-address` прибит к 192.168.100.0/24;
- проверка через реальный модем;
- срок действия ключа узла Tailscale для долгой автономной работы.

## На что смотреть в отчёте

- `rollback armed` — страховка встала. Если строки нет, скрипт не начал работу.
- В режиме `vpn-down` — строка про блокировку:
  - `block confirmed: worker unreachable through the VPN` — прогон засчитывается;
  - `WARNING: the VPN is NOT down` — **прогон не засчитывать**. При
    `auto-detect-interface: true` mihomo привязывает сокет к wlan0,
    а blackhole-маршрут не имеет устройства и может его не поймать.
    Запасной путь: установить nftables и закрыть адреса в output.
- `control-plane DNS` — если `FAILED` или адрес из 198.18.0.0/16, сработала
  подмена fake-ip и Tailscale останется без связи даже при обходе TUN.
- `route with tailscale mark` — должен показывать wlan0, а не Meta.

## Если что-то пошло не так

Откат срабатывает сам. Вручную:

```sh
sudo /home/dmw/projects/monitoring/deploy/net-failover-test.sh rollback
sudo systemctl start mihomo tailscaled
ip -4 route show | grep blackhole      # не должно остаться ни одной строки
```

Если плата потеряла сеть полностью, помогает перезагрузка: blackhole-маршруты
и остановка mihomo не переживают перезапуск, автозапуск служб включён.
Локальная сеть 192.168.100.0/24 выведена из TUN, поэтому SSH
на 192.168.100.196 продолжает работать независимо от состояния VPN.

## Чем продолжить после прогона

Прислать в новую сессию разработки:

1. `/tmp/net-inspect.txt` (или его хвост).
2. `/var/log/monitoring-net-test.log`.
3. Заполненную таблицу результатов SSH извне.

Известные задачи, ожидающие этих данных:

- `route-exclude-address` прибит к 192.168.100.0/24: при смене подсети DHCP
  пропадёт и SSH по локальной сети.
- sshd: `PermitRootLogin yes` и `PasswordAuthentication yes` — пересмотреть
  до выхода в tailnet.
- Проверять имена control plane после каждого перезапуска mihomo: DNS-линк
  Meta появляется заново и снова может отдать fake-ip.

Резервные копии конфигурации mihomo складывает шаг 1 в `/root/mihomo-backup/`,
права 0700; в Git они не попадают.

Не считать независимость SSH достигнутой до прохождения всех состояний.
